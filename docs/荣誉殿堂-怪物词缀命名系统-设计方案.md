## 1. 问题与目标

### 1.1 当前问题

荣誉殿堂目前的"怪物名"是 **Sin 级固定种类名**（如「傲慢-终刃绝影」），同一宗罪的所有历史记录名字完全相同。结果：

- 玩家无法从名字区分"我第 3 局那只贪婪"和"我第 11 局那只贪婪"；
- 玩家的**构筑选择**没有在局外留下任何身份痕迹；
- 荣誉殿堂的"长线成就感"（`Meta_Progression §5.1`）只能靠数字表格承担，缺少可记忆、可讲述的符号。

### 1.2 目标

> 让**同一构筑恒定生成同一个独特名字**，让**不同构筑生成不同名字**，且名字本身可被玩家反向读出"这只怪擅长什么"。

参考物：暗黑破坏神 / 流放之路的怪物词缀命名（`Sharp Swift Cruel <Base>`）。本项目的差异是：**词缀不来自随机 Roll，而来自玩家自己的 BD（Card 清单）**——这正好把"我构筑了它"这件事转成名字。

命名在两个场景消费：

| 场景 | 位置 | 玩家读到的意思 |
|---|---|---|
| **局外回顾** | 荣誉殿堂条目（§10 Phase 2） | 「这是**我**造的那只怪」 |
| **局内遭遇** | Elite 入场横幅 / 世界名（§10A） | 「这是**别人**造的那只怪，正在打我」 |

第二个场景是 v2 新增，且它才是本系统真正的闭环：玩家在自己的荣誉殿堂里看到「远诱阔口贪噬终食之暴食」，某天在别人局里也会以这个名字出现——`03_PRESENTATION §21`「其他玩家历史高投资 Build Snapshot 侵入本 Run」由此获得一个具体的、可辨识的载体，而不只是一个变强的怪。

### 1.3 硬约束（不可违反）

| 约束 | 来源 |
|---|---|
| 荣誉殿堂**不提供任何战斗加成** | `Meta_Progression §5.1`、Decision 35 |
| 名字**不得读成稀有度 / 品质等级** | `03_PRESENTATION §12`（Card 无稀有度） |
| 所有玩家可见词汇**必须走 Text Key**，不得硬编码 / 不得烧进贴图 | `Dual_Line §1` |
| 需要**Mythic / System 双线**，且"一事两译、机制唯一" | `Dual_Line §1`、`03_PRESENTATION §12` |
| 明线避免武侠 / 仙侠 / 东方古风 / 互联网梗 | `Card_System §6`、`03_PRESENTATION §12` |
| 术语不得无控制地增生同义词 | `03_PRESENTATION §29`、`Dual_Line §6` |
| Card 删除 / 改版后历史记录**仍可查看**并标记失效 | `Meta_Progression §5.9` |

### 1.4 明确的非目标

- 不引入任何词缀带来的数值效果、Buff、解锁或成长；
- 不引入随机词缀（名字必须由 BD 确定性派生，不 Roll）；
- 不做词缀交易 / 词缀重铸 / 词缀收集页等新玩法；
- 不在本方案内决定最终词汇的文学定稿（词表需 Owner 审稿，见 §13）。

## 3. 系统总览

```text
该 Sin 的 Card 清单（cardIds / bdData）
        │
        ├─ ① 过滤失效 ID（内容版本兼容）
        ├─ ② 查词缀目录：effectId → { 词, 轴, 权重, 槽 }
        ├─ ③ 打分 + 轴/槽排斥 → 贪心取 Top N（N = 1~4）
        ├─ ④ 按固定轴序排列（与取得顺序无关 → 确定性）
        └─ ⑤ 得到中性词序列 "远诱|阔口|贪噬|终食"
                │
                ├─→ 【局外】写入荣誉记录 epithetCache，套模板显示
                │        「远诱阔口贪噬终食之暴食」
                │
                └─→ 【局内】随快照 monsterType 上传 → 他人局注入端拆分套模板
                         「精英怪远诱阔口贪噬终食之暴食出现！」
```

两条消费路径**共用同一个生成函数**（§10A.6），保证"我的怪"和"别人遇到的我的怪"同名。

四条设计原则：

1. **确定性（Determinism）**：同一 `cardIds` 集合 → 恒定同一名字。集合本身无序，算法内部先排序再打分，tie-break 完全确定，**不使用随机数**。
2. **可反向读**（Legibility）：玩家看到"三重"应能想起「王冠军势」。词缀与卡是 1:1 映射，不做词汇复用。
3. **深度而非品质**（Depth, not Rarity）：词数只反映"这只怪被投资了多少"，UI 不得配合任何色阶 / 星级 / 品质文字。
4. **零 Gameplay 耦合**：命名系统是纯读取 + 纯展示层，不回写任何战斗数据。

## 4. 词缀词库规范

### 4.1 覆盖范围

| 范围 | v1 是否需要词 | 理由 |
|---|---|---|
| 49 张 Sin 卡（MonsterType + TypeGrowth） | **必需** | 荣誉记录 `cardIds` 只含这些（`Meta_Progression §6.1`） |
| 9 张基础通用（`UB-*`） | 不产出 | 不进 `bdData`，v1 无消费方 |
| 7 张全局槽位质变（`GX-*`） | 不产出 | 同上 |

> 若未来 Owner 决定把通用 / 全局卡纳入命名（例如给 First Clear 的"完整称号"用），必须**另起一个前缀环**（如置于罪名之后的后缀位），且新词与 §附录 A 的 49 词**全局不重复**。不要现在预产出，避免撞词与无效工作。

### 4.2 单词硬规范

| 项 | 规范 |
|---|---|
| 字数 | **恒定 2 个汉字**。不允许 1 字或 3 字，否则模板宽度不可控 |
| 词性 | 可直接前置修饰名词的**形容词 / 状态性偏正词**（「迅捷」「阔口」√；「攻击」「使用」✗） |
| 唯一性 | **同一 Sin 内绝对不重复**；跨 Sin 允许重复但需 Owner 认可（当前词表仅 `不息`(WR-S03) 与 `迅潮`(LU-TG01) 曾候选相同，已拆开） |
| 用字排斥 | 同一 Sin 内任意两词**不得共用汉字**（避免「锋利 + 锐利」这类拼出来发音重复的名字） |
| 语域（明线） | 遵循 `Card_System §6` 各罪母题：傲慢=王座/宣判、怠惰=遗命/沉眠、暴食=饥神/圣餐、嫉妒=镜/眼/雷霆、愤怒=末日/锁链/殉身、贪婪=圣油/圣库/万手、色欲=誓约/锚印/系带 |
| 语域（暗线） | 冷静技术语汇：速率 / 实例 / 协议 / 写入 / 转化 / 隔离 / 派生 |
| 生僻字 | 禁止（如「餍」「饕」不用）；小学高年级可读为下限 |
| 禁止 | 武侠 / 仙侠 / 东方古风 / 网络梗 / 品质词（「传说」「稀有」「至尊」「神级」） |
| 禁止 | 直接暴露数值（「五十」「三秒」） |

### 4.3 双线要求

每个词缀需要三个字段，与 `TextEntry` 现有结构天然对齐：

| 字段 | 内容 | 示例（`PR-A01 王冠军势`） |
|---|---|---|
| `text`（中性） | 机制中性词，用于 Neutral Display Profile 与调试 | `三重` |
| `mythicText` | 明线词（默认与中性同，仅在语域需要时分化） | `三重` |
| `systemText` | 暗线词，技术语汇 | `三实例` |

暗线词允许 3 字（因为 System 模板用「·」分隔而非直接拼接，宽度约束不同）。**明线词必须 2 字**。

Text Key 约定（沿用 `CardData.textKey` 命名空间，零新机制）：

```text
card.<effectId>.name     ← 已存在（卡名）
card.<effectId>.desc     ← 已存在（卡描述）
card.<effectId>.epithet  ← 本方案新增（词缀词）
```

## 5. 词缀轴（Axis）与代表性权重

### 5.1 为什么需要"轴"

若只按权重取 Top 4，满构筑的傲慢可能选出「远击 + 疾巡 + 三重 + 交错」——四个词全是"攻击变多变远"，读起来像同一句话说四遍。**轴（Axis）用于保证 4 个词描述 4 个不同侧面**。

### 5.2 十轴定义

| # | 轴 | 语义 | 明线语感位次 |
|---|---|---|---|
| 1 | `Rate` 速率 | 速度、频率、冷却 | 1 |
| 2 | `Reach` 距程 | 距离、远程化 | 2 |
| 3 | `Scale` 幅度 | 范围、体量、持续时长 | 3 |
| 4 | `Count` 数目 | 数量、分裂、增殖、次数 | 4 |
| 5 | `Shape` 形态 | 形态替换、路径重写、弹幕形状 | 5 |
| 6 | `Bind` 缚印 | 标记、减速、牵引、储存 | 6 |
| 7 | `Derive` 派生 | 延迟派生、路径残留、二次结算 | 7 |
| 8 | `Interact` 交锋 | 切断、吞噬、压制、反射 | 8 |
| 9 | `Endure` 存续 | 防护、回复、低耐久响应 | 9 |
| 10 | `Lethal` 杀伐 | 伤害提升、处决 | 10 |

**排列规则**：最终名字中的词按"语感位次"升序排列，**与选取顺序、取得顺序无关**。这既保证确定性，也让最"重"的词（杀伐 / 存续）紧贴中心词，符合中文修饰语的轻重节奏——用户示例「锋利迅捷残酷之傲慢」的末位「残酷」正是 `Lethal`。

> 位次表为可配置项，不写死在代码里（`03_PRESENTATION §8.1`「策划可在不修改代码的情况下配置」精神）。

### 5.3 代表性权重（Base Weight）

按 Canonical 对卡的机制定位分档，默认值：

| 档 | 权重 | 判定 | 例 |
|---|---:|---|---|
| Type Growth | **1000** | `CardCategory.TypeGrowth` | `PR-TG01`、`LU-TG01` |
| 形态质变 / 目标方式解锁 / 高阶 Interaction | **80** | Canonical「机制类别」含"质变 / 解锁 / 高阶Interaction / 替换" | `PR-A02`、`GL-A03`、`GL-S03` |
| 跨槽联动 / 派生 / 击杀增殖 | **65** | 含"联动 / 派生 / 路径 / 再索敌 / 复现" | `PR-X01`、`EN-S01`、`GR-A03` |
| 资源 / 状态 / 条件强化 | **55** | 含"Resource / 状态 / 条件 / 转化 / 储存" | `GR-A01`、`EN-R01`、`GL-S01` |
| 单轴基础强化 | **35** | 只动距离 / 范围 / 速度 / 时长 | `PR-A04`、`WR-S03` |

**Type Growth 权重 1000 = 强制入选并置于其轴位**。理由：`Card_System §3` 明确 Type Growth 的价值是"该罪整体开始更像它自己"——这正是命名要表达的东西。

权重是**策划可覆盖的显式字段**，上表只是默认映射，不是硬编码分类推断。

## 6. 选词算法

### 6.1 词数规则

| 该 Sin 的有效卡数 | 词数 N |
|---:|---:|
| 1 | 1 |
| 2 | 2 |
| 3 | 3 |
| ≥ 4 | **4（上限）** |

上限 4 的理由：4 词 = 8 字 + 连接词 1 字 + 罪称谓 2 字 = **11 字**，1920×1080 下荣誉殿堂条目标题行可单行容纳（对照 `局外系统UI生成提示词` §11 的排版预算）。5 词起必然折行或缩字号，破坏"庄严登记"的排版秩序。

### 6.2 打分与贪心选择

```text
输入：cardIds（该 Sin 记录的 Card ID 清单）

step 0  过滤：丢弃词缀目录中不存在的 ID（含已删除卡）
        → 若剩 0 条，走 §8.3 兜底命名
step 1  排序：按 effectId 字典序排序（消除集合无序性）
step 2  N = clamp(有效条数, 1, 4)
step 3  重复 N 次：
          对每个未选候选 c 计算
            score(c) = baseWeight(c)
                     × axisPenalty(c)     // 已选集合中同轴数量 k → 1 / 2^k
                     × slotPenalty(c)     // 已选集合中同槽数量 m → 0.8^m
          取 score 最大者；同分则比 baseWeight；再同分则 effectId 字典序小者胜
step 4  已选 N 个词按 §5.2 语感位次升序排列
step 5  套 §7 模板输出
```

- `axisPenalty` 用**惩罚**而非**硬排斥**：满构筑的贪婪 8 张卡里可能出现同轴集中，硬排斥会导致凑不满 4 词。
- `slotPenalty`（Movement / Attack / Special / Body）是次级去重，让名字尽量横跨三槽，呼应 `03_PRESENTATION §15`「三槽动作身份」。
- 全流程**无随机数**、**无时间依赖**、**无玩家 ID 依赖**。同一 BD 在任何设备任何时间生成同一名字。

### 6.3 走查示例：满构筑傲慢

`cardIds = [PR-A01, PR-A02, PR-A03, PR-A04, PR-M01, PR-S01, PR-X01, PR-TG01]`（8 张，N=4）

| 轮 | 胜出 | score 说明 |
|---:|---|---|
| 1 | `PR-TG01` 迅捷 (Rate, 1000) | Type Growth 强制置顶 |
| 2 | `PR-A01` 三重 (Count, 80) | `PR-A01` / `PR-A02` / `PR-A03` 三张同为 80 且同槽(Attack)，纯靠 effectId 字典序决胜 |
| 3 | `PR-A02` 交错 (Shape, 80×0.8=64) | 同槽惩罚生效；与 `PR-A03`(Interact, 64) 同分，再比字典序 |
| 4 | `PR-X01` 遗锋 (Derive, 65×1.0=65) | 胜过 `PR-A03` 斩绝 (Interact, 80×0.64=51.2)——跨槽(Special)无惩罚 |

已选 = {迅捷(Rate,1)、三重(Count,4)、交错(Shape,5)、遗锋(Derive,7)}
按位次排列 → **「迅捷三重交错遗锋之傲慢」**

> 该示例暴露一个语感问题：`PR-A01/A02/A03` 三张同为 80 分且同槽，靠字典序决胜，语感上未必最优。**缓解手段**：策划用显式 `weight` 微调（例如把标志性最强的 `PR-A03 斩绝` 提到 85），把决胜权交回人手，而不是让字典序做美学决定。这是 §13 的 Open Decision 之一。

## 7. 命名模板与双线

### 7.1 三条线的模板

| 线 | 模板 | 示例 |
|---|---|---|
| **Mythic** | `{词1}{词2}{词3}{词4}{连接词}{罪称谓}` | 「迅捷三重交错遗锋**之**傲慢」 |
| **System** | `{罪系统名} · {暗线词1}/{暗线词2}/… · Rev.{有效卡数}` | 「Pride Carrier · 速率统调/三实例/十字面/路径派生 · Rev.8」 |
| **Neutral** | `{罪中性名}（{有效卡数} 卡构筑）` | 「傲慢（8 卡构筑）」 |

- 连接词默认「之」，可配置为「的」/「·」/空。
- 罪称谓三线各一份，走 Concept Key（`03_PRESENTATION §29`「每个稳定 Concept Key 需要支持 Neutral / Mythic / System 映射」）：

| Sin | Neutral | Mythic | System |
|---|---|---|---|
| Pride | 傲慢 | 傲慢 | Pride Carrier |
| Sloth | 怠惰 | 怠惰 | Sloth Carrier |
| Gluttony | 暴食 | 暴食 | Gluttony Carrier |
| Envy | 嫉妒 | 嫉妒 | Envy Carrier |
| Wrath | 愤怒 | 愤怒 | Wrath Carrier |
| Greed | 贪婪 | 贪婪 | Greed Carrier |
| Lust | 色欲 | 色欲 | Lust Carrier |

> Mythic 与 Neutral 目前同值，是**故意的**：`Dual_Line §6` 要求同一概念不增生同义词；罪名本身已是双线共用的稳定术语（`03_PRESENTATION §29` 已把 Seven Sins 列为"当前稳定"）。差异全部落在词缀与结构上。

### 7.2 黑色幽默从哪来

`03_PRESENTATION §4`：「幽默来自同一行为被两套认真语言解释」。本系统天然贴合：

```text
Mythic：迅捷三重交错遗锋之傲慢
System：Pride Carrier · 速率统调/三实例/十字面/路径派生 · Rev.8
```

同一只怪，一边是被神话册封的称号，一边是配置项串联的版本号。**两边都必须认真**，System 侧不得写成吐槽（禁止「又一个自以为是的样本」这类）。

### 7.3 显示线选择

沿用现有 `NarrativeDisplay` / Display Profile 机制，不新增开关：

- 载体分类建议新增 `NarrativeCarrier` 语义位（或复用 `General`）；
- 默认行为遵循 `Meta_Progression §4.7` 的既有约定：**First Clear 前默认 Mythic，之后默认 System 且可手动切换**；
- 荣誉殿堂条目**始终并列显示中性数据区**（BD 深度 / 击杀 / 战绩），所以名字切线不影响可读性，符合 `Dual_Line §1`「默认不并排显示同一条文本的两版」。

### 7.4 同名去重（世代标记）

同一玩家可能两局构筑出完全相同的 BD → 完全同名。处理：

- **不改名**，在 UI 层为同名组按 `savedAtUnix` 升序追加序号：第 2 条起显示「…之傲慢 · II」「…之傲慢 · III」；
- 序号是**展示层派生**，不写入存档（换设备 / 清档后重新计算不影响语义）；
- 只在真正冲突时出现，单例记录永不带序号。

## 8. 命名生命周期与内容版本兼容

这是本方案最需要 Owner 拍板的技术—设计交界点。

### 8.1 三种方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 纯派生** | 每次打开荣誉殿堂时从 `cardIds` 实时生成 | 零存档变更、零迁移、词表改版立刻全量生效 | 卡池删卡后**老怪会改名**，玩家记忆中的名字消失 |
| **B 纯冻结** | 首次生成即写入存档，永不重算 | 名字永久稳定，成就感最强 | 词表纠错 / 错别字修复无法回溯；需存档字段与 schema 升级 |
| **C 混合（推荐）** | 生成即写入 `epithetCache` + `epithetRev`；展示优先读 cache；卡池变更**不触发改名**，只叠加既有的「历史版本 / 部分内容已失效」标记；提供调试指令批量重算 | 名字稳定 + 词表可纠错 + 与 `Meta_Progression §5.9` 完全一致 | 需 `schemaVersion 1 → 2` 迁移（追加字段，向后兼容） |

**推荐 C**。理由：

- `Meta_Progression §5.9` 已经规定"Card 删除 / 改版后，历史记录标记为「历史版本 / 部分内容已失效」，仍可查看"——这条规则的精神是**保留历史原貌 + 明示失效**，而不是静默重写历史。方案 A 违反这个精神。
- `HallOfFameData` 已有 `schemaVersion` 字段（当前 1），且该文件**不进 `SaveMigrator` 链**、损坏即重置为空，追加两个可空字段的迁移风险极低。
- `epithetRev`（词表版本号）让"错别字修复"可以通过一次显式的策划操作全量重算，而不是每次开界面偷偷变。

### 8.2 失效卡的处理

| 情形 | 处理 |
|---|---|
| 部分 `cardIds` 在当前牌池不存在 | 名字**不变**（读 cache）；条目继续显示现有 `ui.hof.entry.stale_cards` 失效标记 |
| cache 为空（老存档 / 刚迁移） | 用**当前**词表对**当前可识别**的 ID 生成一次并写入 cache |
| 全部 ID 都不可识别 | 走 §8.3 兜底 |

### 8.3 兜底命名

有效词数为 0 时（极端：整个 Sin 的卡全被删除），输出**只有中心词**的名字：

- Mythic：「傲慢」（退化为原有种类名语义）
- System：「Pride Carrier · Rev.0」
- 并附失效标记

不虚构词缀，不显示空「之傲慢」。

## 9. 数据与配置载体

### 9.1 词缀目录放哪：独立 SO（推荐）

| 选项 | 评估 |
|---|---|
| 扩展 `CardData`（加 `epithetAxis` / `epithetWeight` 字段） | ✗ `CardLibrary.asset` 有 49+ 条既有序列化数据，改结构触碰 `.vibe/rules.md §3.3`（`[SerializeField]` 字段顺序 / 类型变更风险）；且词缀是**局外表现**配置，混进 Gameplay 卡数据违反关注点分离 |
| **独立 `CardEpithetCatalog` ScriptableObject（key = effectId）** | ✓ 单文件单表，策划一屏看全 49 词与轴；不动 `CardLibrary.asset`；缺词 = 该卡不参与命名（优雅降级）；与既有 `EliteMonsterCatalog` / `TextCatalog` 的单文件 SO 模式一致 |
| 纯 `TextCatalog` 承载 | ✗ 词能放（`card.<id>.epithet`），但 `axis` / `weight` / `slot` 是**结构化配置**不是文本，塞进文本目录会污染其职责 |

**推荐结构**（提案，非最终 API）：

```text
CardEpithetCatalog.asset
└─ entries[]
     ├─ effectId      : string   // 关联键，如 "PR-A01"
     ├─ epithetTextKey: string   // 默认 "card.<effectId>.epithet"，留空自动推导
     ├─ axis          : enum     // §5.2 十轴
     ├─ slot          : enum     // Movement / Attack / Special / Body / None
     └─ weight        : float    // 留 0 = 按 §5.3 默认档推断
├─ maxEpithetCount   : int  = 4
├─ connector         : string = "之"
└─ axisOrder         : Axis[]     // §5.2 语感位次，可重排
```

**词本身仍走 `TextCatalog`**（`card.<effectId>.epithet` 的 `text` / `mythicText` / `systemText`），SO 只存结构与引用。这样：中文文案统一在文本目录管理（符合现有架构意图），词缀逻辑配置独立可读。

### 9.2 存档字段（方案 C）

```text
HallOfFameEntry（追加，全部可空 / 有默认值）
├─ epithetCache : string   // 已冻结的中性词序列，如 "迅捷|三重|交错|遗锋"
└─ epithetRev   : int      // 生成时的词表版本；0 = 未生成

HallOfFameData
└─ schemaVersion : 1 → 2
```

存**中性词序列**而非成品字符串，理由：切换 Mythic / System 时仍需重新套模板，冻结成品会锁死显示线。

### 9.3 不需要新增的东西

- 不新增网络协议字段（v1 词缀不上传服务器）；
- 不新增 Prefab / 场景引用（`HallOfFamePanel` 是纯代码 UGUI）；
- 不新增 Localization 系统（`TextCatalog` 已足够）；
- 不新增随机数源。

## 10A. Elite 投放侧命名（局内）

> v2 新增。目标：玩家在别人的局里遭遇 Elite 时，看到的是**那个构筑的名字**，而不是「精英·暴食-魔猫」这种种类名。

### 10A.1 为什么这件事值得做

`03_PRESENTATION §21` 要求 Elite 读成「其他玩家历史高投资 Build Snapshot 侵入本 Run」，并明确禁止读成「当前 Run 随机长出几条 Mutation 的普通怪」。

当前实现下，玩家看到的横幅是「精英怪暴食-魔猫出现！」——**这句话完全无法传达"这是别人的东西"**。它读起来就是一只更强的暴食。

换成「精英怪远诱阔口贪噬终食之暴食出现！」之后：

- 名字的**结构**（多个词缀 + 之 + 罪名）本身就是"被人长期投资过"的信号；
- 词缀**内容**直接预告威胁形态——「远诱」告诉你巨口会从远处落点生成，「阔口」告诉你范围翻倍。这同时服务 `03_PRESENTATION §16 Telegraph`：玩家在挨第一下之前就能读到危险类型；
- 玩家自己也在造这种名字（§10 Phase 2），于是**认得出这套命名法**——「这是某个玩家的暴食构筑」这个认知不需要任何教学。

### 10A.2 核心矛盾：名字该在哪一端生成

这是本章唯一的真问题。

| 方案 | 做法 | 致命缺陷 / 代价 |
|---|---|---|
| **注入端生成** | 下发快照只带 `bdData`，遭遇方用**本机**词表算名字 | ✗ **跨版本不一致**：上传者是 v1.3 词表，遭遇者是 v1.5 词表 → 同一只怪在两人屏幕上叫不同名字。荣誉殿堂里叫 A，别人局里叫 B，直接破坏"这是我那只怪"的认同。且遭遇方缺卡时（对方有新卡我没有）算出的名字更短更弱，等于**信息失真** |
| **上传端生成（推荐）** | 上传时把成品名写进 `monsterType`，注入端**直接显示**，不重算 | ✓ 名字随快照走，跨版本恒定；✓ 零新增协议字段（`monsterType` 已存在且已校验非空）；代价：需要下发**中性词序列**才能支持双线切换（见 10A.3） |

**推荐上传端生成**，与 §8 方案 C（生成即冻结）的思路一致：**名字属于那个构筑，不属于观看者**。

### 10A.3 双线的处理（上传端生成带来的新问题）

矛盾：`Dual_Line §1` 要求名字有 Mythic / System 两版并能切换，但快照是**上传时**生成的——上传者的显示线偏好不该决定遭遇者看到什么。

解法：**`monsterType` 不存成品名，存中性词序列**，遭遇端只负责套模板。

```text
上传端写入：monsterType = "gluttony|远诱|阔口|贪噬|终食"
                            └sin┘ └────中性词序列────┘

注入端读取：拆分 → 用本机 TextCatalog 把中性词映射为当前显示线的词 → 套 §7 模板
             Mythic → 「远诱阔口贪噬终食之暴食」
             System → 「Gluttony Carrier · 落点解锁/覆盖翻倍/全量吞噬/低耐久终止 · Rev.4」
```

这样：

- **词的选择**（哪 4 个、什么顺序）由上传端冻结 → 跨版本恒定 ✓
- **词的呈现**（哪条线、什么措辞）由遭遇端决定 → 双线可切换 ✓
- 遭遇端遇到**本机词表没有的中性词**（对方版本更新）→ 该词原样显示（中性词本身就是可读中文，不是 ID），不丢字不报错 ✓

> 这是本章的关键设计。若嫌复杂而直接下发成品 Mythic 名，则 System 线用户会看到明线名字，违反 `Dual_Line §1`。

**兼容性**：`monsterType` 当前是自由 `string`，服务器只校验非空、不解析内容（§2.1 已验证），因此改变其内容格式**不需要改服务器、不需要改协议、不需要数据迁移**。旧格式（纯 catalog 名，无 `|`）按"无词缀"处理，见 10A.4。

### 10A.4 四种投放来源的命名策略

Elite 有四个来源，不能一视同仁：

| 来源 | `bdCount` | 命名 | 理由 |
|---|---:|---|---|
| **在线真实快照**（新格式） | ≥1 | 完整词缀名「远诱阔口贪噬终食之暴食」 | 主路径，本章目标 |
| **在线真实快照**（旧格式，无 `\|`） | ≥1 | 沿用现有 catalog 名「暴食-魔猫」 | 向后兼容：老快照不因新功能而显示异常 |
| **本地 Preset 兜底**（无网 / 空库） | ≥1 | 由 Preset 的 `cardIds` **本机实时生成**词缀名 | Preset 是本地内容、词表必然同版本，无跨版本问题（`Meta_Progression §6.3`：兜底不改变 Run 流程） |
| **定时投放**（`bdCount = 0` 空快照） | 0 | **不加词缀**，用 catalog 名 | 它没有历史构筑，强行编词缀等于**虚构一个不存在的玩家**，违反荣誉殿堂"异步战绩来自真实回传、非推测"的同源精神（`§5.10`） |

最后一条尤其重要：**不得给无构筑的精英伪造构筑名**。宁可让它看起来普通，也不能让玩家以为遭遇了一个不存在的构筑。

### 10A.5 表现落点

| 落点 | 现状 | 建议 |
|---|---|---|
| 入场横幅 | `EliteAnnouncementUI` 单行 980×86、字号 30、硬编码 `精英怪{0}出现！` | 文案迁入 TextCatalog；4 词名（11 字）+ 前后缀共约 19 字，**字号 30 下 980px 可容**，但需实测；`enableWordWrapping` 已开启，最坏情况折行不截断 |

### 10A.6 与荣誉殿堂的一致性保证

同一个构筑必须在两处**同名**：

```text
我的荣誉殿堂         epithetCache = "远诱|阔口|贪噬|终食"   （§9.2 存档）
        ↕ 必须一致
我上传的快照         monsterType  = "gluttony|远诱|阔口|贪噬|终食"
        ↓
别人局里的横幅       「精英怪远诱阔口贪噬终食之暴食出现！」
```

实现要求：**两处必须调用同一个生成函数**（§10 Phase 1 的纯函数生成器），不得各写一份。

时序细节：`HallOfFameStore.UpsertFromSnapshots` 与 `EliteBuildDirector.BuildSnapshots` 本就消费**同一份** `SnapshotEntry` 数据（`HallOfFameStore.cs` L95-113 由前者调用后者产物），因此把词序列在 `BuildSnapshots` 里算一次、两边共用是自然的，无额外一致性风险。

### 10A.7 隐私与内容安全

词缀名**完全由 Card ID 派生、不含任何玩家输入**，因此：

- 不存在昵称 / UGC 文本注入风险；
- 不泄露 `playerId`（横幅不显示来源玩家）；
- 无需内容审核（对照 `Meta_Progression §7`「反作弊、内容审核…后续里程碑」——本功能天然不需要）。

这是"从 BD 派生"而非"玩家自命名"的额外收益，值得在设计上守住：**不要在后续版本加入玩家手动命名**，否则以上三条全部失效。
